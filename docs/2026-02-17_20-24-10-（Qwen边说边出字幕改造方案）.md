# Qwen-ASR-Realtime 实现“边说话边出文字”的字幕改造方案

生成时间：2026-02-17 20:24:10（本地时间）

## 1. 背景与问题现象

当前项目已接入 **Qwen-ASR-Realtime（主进程直连 + IPC）**。实际体验中：

- **火山引擎（Volc）**：能“跟着音频”快速出现字幕，观感接近同步。
- **Qwen**：经常需要“说完一小段”后才出现字幕，实时性明显偏弱。

## 2. 结论（原因拆解）

要实现“边说边出字”，需要同时满足两件事：

1) **服务端确实提供高频的中间结果**（partial / text / delta 等）；  
2) **客户端要正确解析并高频刷新 UI**（中间结果事件必须被映射为字幕刷新）。

针对当前项目的实现，Qwen 的延迟通常来自两类问题（可能同时存在）：

### 2.1 协议事件映射不完整（最常见、最值得先修）

Qwen Realtime 的中间转写并不一定只通过 `delta/transcript` 这套字段表达，中间结果常见是独立事件（例如 `.text`）并包含 `text` / `stash` 等字段。

如果主进程 `electron/main.ts` 的 WS 消息解析只处理 `delta/transcript`，就会出现：

- **真正的高频中间结果没有被转成 IPC partial**；
- 渲染进程只能等到分段完成后拿到“更完整/最终”的文本，于是观感像“按段出字”。

### 2.2 识别触发时机过度绑定 VAD（天然按段）

当前 Qwen `session.update` 中启用了 `turn_detection.type = server_vad`（服务端 VAD）。

VAD 的设计目标是“自然分句”，并不是“连续逐字吐出”。当静音不明显、或 `vadSilenceDurationMs` 较大时：

- 分段结束更晚；
- 以“分段完成”驱动更新的实现就会更慢。

> 备注：即使你在控制台看到了 `onPartial`，也要警惕它是否其实是“段尾的一次性整段 partial”，而不是“持续增量”的 partial。

## 3. 当前工程链路（便于定位改动点）

- 渲染进程字幕刷新逻辑：`frontend/src/hooks/useASR.ts`
  - 监听 `provider.on('onPartial', ...)` 并立刻调用 `captionUpdateText` 更新字幕窗口
- Qwen Provider：`frontend/src/providers/implementations/QwenProvider.ts`
  - 将主进程 IPC 的 `partial/final` 转成 `emitPartial/emitFinished`
- Qwen 主进程 WS 解析：`electron/main.ts`（`handleQwenWsMessage`）
  - 负责把服务端事件解析成 `asr:qwen:event`（partial/final/state/error）

因此，“边说边出字”最关键的改动点在 **`electron/main.ts` 的消息解析与映射策略**。

## 4. 改造目标与验收标准

### 4.1 目标

- 讲话过程中，字幕能以 **200~500ms 粒度**持续刷新（主观接近同步）。
- 结束说话后，能在 **≤ 1s** 内收敛到更稳定的文本（最终稿/更稳的 partial）。
- 与 Soniox / Volc 互不影响（回归不破坏）。

### 4.2 非目标（本轮不强求）

- 不追求“完美断句/完美标点”，实时字幕优先。
- 不在本轮完成大规模 Provider 抽象重构，仅做局部增强即可。

## 5. 方案设计（两条路径）

推荐实施顺序：**先做方案 A**（低风险、最小改动），若效果仍不达标，再加方案 B。

---

## 5A. 方案 A（推荐）：补齐中间结果事件映射，让字幕跟随 `.text` / `text+stash`

### 核心思路

在主进程 `handleQwenWsMessage` 中：

- 识别并处理“中间转写事件”（例如 `.text`）
- 将其中的 `text`（已确认文本前缀）+ `stash`（草稿后缀）拼成实时展示串
- **立刻发 IPC `partial`** → 渲染进程立刻刷新字幕

### 关键实现要点（伪代码级别）

1) 解析消息后，优先识别：
   - `conversation.item.input_audio_transcription.text`
     - 取 `text` + `stash`（或按服务端实际字段名做兼容）
     - `session.partialText = display`（建议“替换”，不要累加）
     - `pushQwenPartial(session, msg)`

2) 对最终事件：
   - `conversation.item.input_audio_transcription.completed` 或 `session.finished`
     - 取 `transcript`
     - 维护 `session.committedText`（追加或覆盖，需做去重策略）
     - `session.partialText = ''`
     - 触发 IPC `final`（或继续按 `partial` 更新字幕也可以，但要避免重复追加）

3) 保留现有节流：
   - `pushQwenPartial` 当前 60ms 节流已经足够，避免 UI 过载

### 预期效果

- 如果服务端确实高频发送 `.text`，字幕将显著更“跟嘴”。

### 风险与对策

- 风险：字段名/事件名在不同文档或版本存在差异  
  对策：做事件名与字段名兼容（例如同时尝试 `text`/`stash`/`delta`/`transcript`），并通过 debug 统计确认真实分布。

## 5B. 方案 B（实时字幕模式）：Manual + 定时 commit（不等静音）

### 适用条件

当你完成方案 A 后发现：

- 服务端 `.text` 仍然不够“连续”（例如只在段尾出现），或
- 长段连续讲话时仍然明显“按段出字”

则需要“从机制上”改变识别触发时机：不要完全依赖 `server_vad`。

### 核心思路

新增一个“实时字幕模式”：

- `turn_detection = null`（Manual）
- 主进程按固定间隔（例如 250ms）发送 `input_audio_buffer.commit`
- 让服务端更频繁地产出可展示的转写结果

### 配置建议（新增项）

在 Qwen 配置中新增：

- `turnDetectionMode: 'server_vad' | 'manual'`（默认 `server_vad`，保证兼容）
- `commitIntervalMs?: number`（仅 `manual` 生效，建议 200~400）

### 主进程会话策略

1) `connect` 后的 `session.update`：
   - `manual`：`turn_detection: null`
   - `server_vad`：保持现有 `turn_detection` 参数（`threshold/silence_duration_ms`）

2) 音频推流：
   - 仍然高频 `input_audio_buffer.append`
   - 维护“最近一次 append 时间”，作为是否需要 commit 的依据

3) 定时器（每 session 一个）：
   - 若自上次 commit 后出现过 append，则发送一次 `input_audio_buffer.commit`
   - commit 后继续 append，形成“持续滚动提交”

4) 停止与收敛：
   - stop：停止定时器 → 最后 commit（可选）→ `session.finish` → 等最终事件

### 预期效果

- 连续讲话基本不停顿时，也能以 200~400ms 粒度持续更新字幕，观感最接近“边说边出字”。

### 风险与对策

- 成本/流量：commit 频率提升可能增加事件量  
  对策：提供开关（仅“实时字幕模式”启用），默认仍用 `server_vad`
- 文本碎片化：更频繁的 commit 可能使断句更碎、标点更不稳  
  对策：字幕 UI 优先实时；最终稿仍用完成事件收敛，或在停止时请求更稳的二遍结果（如有）

## 6. 配套优化建议（可选）

### 6.1 降低前端音频采集基础延迟

`frontend/src/utils/audioProcessor.ts` 当前 `bufferSize=4096`，在 16kHz 下约 256ms 一包。可考虑降到 2048/1024，以降低“采样到发送”的底层延迟。

权衡：包更小 → IPC 更频繁 → CPU/GC 负担上升，需要观察。

### 6.2 可观测性（建议加一个 Debug 开关）

建议统计并输出（抽样）：

- Qwen 事件 type 分布（尤其是 `.text/.completed/session.finished`）
- `onPartial` 到达频率与平均间隔
- 首帧延迟（开始说话到第一条 partial）

注意：日志不要包含 `apiKey`，raw 消息如需输出需做脱敏。

## 7. 验收与回归测试清单

### 7.1 实时性验收

- 连续讲话 10~20 秒：
  - 字幕是否持续滚动刷新（而非停很久突然出一大段）
  - 平均刷新间隔是否稳定（目标 200~500ms）

### 7.2 收敛与停止

- 点击停止后：
  - 能收到最终/更稳定文本（不丢字、不重复）
  - 会话正确关闭、资源回收（WS/定时器/IPC listener）

### 7.3 回归

- Soniox / Volc 行为不变
- 切换 provider 不串话（按 `webContents.id` 隔离会话）

## 8. 推荐落地顺序（最省风险）

1) **先落地方案 A**：补齐 `.text` / `text+stash` 映射 → 观察实时性是否显著改善  
2) 若仍偏慢：加入 **方案 B 的“实时字幕模式”**（manual + commitInterval）  
3) 最后再做可选优化：减小 `AudioProcessor` bufferSize、完善 debug 统计
